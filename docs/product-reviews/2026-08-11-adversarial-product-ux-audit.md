# “咋剪发”全页面对抗性产品与移动端 UX 审计

> 审计日期：2026-08-11
> 报告版本：V3，已追加 Product Manager、Product Design 与 Playwright Interactive 三套 Skill 交叉复审
> 审计基线：`agent/zajianfa-hairstyle-library` / `91c248224fa054f1691e249629c48e65eaaeb136`
> 审计目标：不是证明功能能运行，而是判断普通用户是否能理解、愿意使用、感到内容属于自己，并能在真实理发场景中完成任务
> 审计设备：390 × 844 手机视口为主，结合既有 360/390/430、桌面、200% 字体及错误状态证据
> 本轮范围：只审计并出报告，不修改产品功能或视觉代码

## 1. 执行结论

当前版本不是一个可以直接交给普通用户体验的消费级产品，而是一个**技术能力较完整、产品组织尚未完成的功能验证版**。

它已经有不少真实底座：本机档案、精选发型、私人参考、收藏夹、计划、沟通卡、本地图片压缩去 EXIF、隐私遮罩、剪后记录、复刻与避雷都能保存和刷新；错误状态也普遍诚实，不会用另一条数据冒充缺失内容。这些是值得保留的基础。

但从用户体验看，当前存在五个系统性问题：

1. **“这是为我定制的”没有成立。** 用户档案没有照片、性别或风格呈现、头脸与发型困扰；已填写的数据也不参与发型排序、首页主视觉或沟通卡生成。
2. **核心记录任务违背真实场景。** 理发后要面对六类照片、两列密集输入和默认 5 分/默认复刻；其中“理发中”照片明显不符合用户在剪发时的行为。
3. **页面像数据库管理器，不像个人发型工具。** 档案按主档案、计划、记录、标准发型、避雷、沟通卡分成六块，空态堆叠，照片与个人记忆反而缺席。
4. **视觉系统只是覆盖旧页面，没有完成统一重构。** 首页与发型库接近新方向，档案、计划、记录、沟通卡和遮罩仍像不同产品；固定底栏和操作坞互相叠加。
5. **已有真实视觉回归。** 剪后记录详情中的“已存为标准发型”区域出现浅色文字叠在白色卡片上，几乎不可读。这不是审美分歧，而是上线阻断。
6. **界面缺少统一的物理感和操作反馈。** 少数首页、发型库和底栏操作已经接入按压反馈，但档案、计划、记录、沟通卡、表单和遮罩中的大量按钮仍像普通文字或平面色块；卡片没有稳定体积层级，拖动与松手反馈也没有覆盖真实任务。

**发布判断：不建议现在开放陌生用户测试，更不建议收费。** 应先完成“个人发型护照 + 剪前/剪后记录 + 个性化解释 + 理发师一屏沟通”的核心重构，再做全页面视觉统一。

## 2. 审计覆盖与证据

本次不是只看用户提供的四张截图，而是检查了完整产品路由、主要状态、源码数据契约和既有端到端证据。

### 2.1 覆盖范围

- 路由表：23 个路由条目，包含 22 个可到达产品路径和 1 个兜底 404；
- 用户页面：17 个被路由使用的 Vue 页面视图；另检查了已退役但仍留在源码中的投票页面；
- 自动化：19 个 Playwright 场景；
- 视觉证据：审阅既有约 70 张页面截图，并重新生成 29 张 390 × 844 审计截图；
- 数据模型：`HairProfile`、`HaircutPlan`、`Candidate`、`BarberBrief`、`HaircutRecord`、`HaircutPhoto`、`AvoidRule`、`StandardStyle`；
- 关键状态：新用户、已有档案、空收藏、已收藏、私人参考新增/详情/展示、计划、沟通卡、记录详情、图片处理、存储失败、资源不存在、404、遮罩编辑器。

### 2.2 可复核事实

| 项目 | 当前实现事实 | 产品影响 |
| --- | --- | --- |
| 档案照片 | `HairProfile` 没有照片字段，也没有 profile photo 表 | “我的档案”无法形成视觉身份 |
| 性别/风格呈现 | 档案无字段；精选内容自身有女性化/男性化/中性标签但 UI 不使用 | 男女及非二元用户无法表达偏好，内容也无法为我排序 |
| 个性化 | 档案字段主要只在档案总览重新显示 | 填写成本没有换来推荐价值 |
| 沟通卡继承 | 新沟通卡默认空白，只默认选第一个候选 | 档案偏好、避雷规则、精选沟通指南没有自动流入 |
| 理发照片 | 六阶段：剪前、理发中、未造型、已造型、洗后、第 7 天 | 任务负担过重，与用户最新需求冲突 |
| 首页提醒 | 仍会要求补洗后照和第 7 天照片 | 用户完成一次记录后还被追着补作业 |
| 店铺信息 | 只有店铺名称，无地址/位置字段 | 无法区分分店，也不利于复刻 |
| 表单默认值 | 新档案默认直发/中等/10 分钟/隔天洗；新记录默认 5 分和复刻 | 未确认信息被写成事实，历史数据失真 |
| 移动端密度 | 记录页双列输入约 156px；原生文件控件约 135.5px、11.52px | 文本与文件名折叠，手指操作困难 |
| 字号 | 底栏约 10.56px；候选按钮约 10.72px；部分主标题 54.6–62.4px | 视觉资源分配反了：标题过大，任务信息过小 |
| 样式体量 | 三份主样式合计约 6,892 行，archive/form/record selector 多处重复 | 新旧规则互相覆盖，已产生白字白底回归 |
| 理发师展示 | 无屏幕常亮、临时标注、关键点一屏模式 | 现场需要反复滚动，无法真正“递给理发师看” |
| 本机数据 | 无账号符合当前边界，但无完整导出/恢复 | 清缓存或换机后个人照片与历史可能全部丢失 |
| 触觉交互覆盖 | 已有 `v-tactile` 只覆盖首页、我的、底栏和部分发型库控件；拖动轨道主要只用于筛选条 | 新旧页面反馈不一致，用户无法通过视觉和动作预测什么可按、什么可拖 |

## 3. 严重度定义

- **Critical**：阻止核心内容阅读、可能让用户做出错误决定或直接破坏信任；必须立即修复。
- **P0**：开放陌生用户测试前必须完成，否则核心承诺不成立或关键任务难以完成。
- **P1**：影响理解、效率、回访和品质感，应在首轮公开体验前完成。
- **P2**：一致性、精致度和维护问题，可在核心闭环稳定后处理。

## 4. Critical：真实上线阻断

### C-01 剪后记录结果出现近似白底白字

记录详情中的 `REPEAT / 已存为标准发型` 使用了旧版浅色文字规则，但新版把容器背景改成白色，导致核心结果几乎不可见。

这说明当前视觉并非单纯“不够好看”，而是多层 CSS 覆盖已产生功能级回归。该区域恰好承载“下次能否复刻”的核心结论，用户可能误以为没有保存成功。

**修复门槛：**建立稳定语义色 token；删除受影响页面的旧规则；自动检查正文、弱文案、按钮、焦点和状态文本对比度，不能只靠截图目测。

## 5. P0：开放陌生用户前必须解决

### P0-01 “个人发型档案”实际上只是通用文字表

档案只有称呼、发质、发丝粗细、发量、打理分钟、洗发频率和备注。没有当前发型照片、正侧后角度、头型/脸型、自身困扰、发旋、发际线、容易贴或炸等高信号信息。

结果是：档案里的文字换到任何人身上都成立；用户无法一眼确认“这是我的头发”。

**必须改为“个人发型护照”：**首屏以用户真实照片和最近剪前/剪后对比为主；文字退到辅助摘要。

### P0-02 性别与风格呈现缺失

产品面向不限性别用户，但档案没有任何相关字段。精选库虽然给六款内容写了女性化、男性化、中性呈现，界面没有筛选或与用户档案匹配。

建议拆成：

- 性别资料：女、男、非二元、自定义、不愿透露；
- 发型呈现偏好：偏女性化、偏男性化、中性、开放探索。

推荐主要依赖呈现偏好、头发条件和维护意愿；性别不应成为禁止查看某款发型的硬门槛。

### P0-03 用户填写的数据没有产生个性化结果

发型库具备发质、粗细、维护时间等内容标签，用户档案也有相应字段，但二者没有连接。首页主视觉也不读取档案条件。

用户付出了填写成本，却只得到“把刚填的文字再念一遍”。这是当前最严重的产品价值断裂。

**第一阶段无需真实 AI：**用可解释的本地规则排序，直接显示“为什么更适合你”和“现实取舍”，不要输出虚假的匹配百分比。

### P0-04 档案、发型详情、避雷和沟通卡是四个数据孤岛

精选详情已经有整体、顶部、刘海、两侧、鬓角、后脑、最在意和绝对不要；档案有个人偏好；历史有避雷规则。但创建沟通卡时所有内容仍是空白，只默认选中第一个候选。

这会让用户重复抄写，且极易遗漏真正重要的信息。

**必须形成链路：**候选指南作为初始草稿，叠加档案偏好和已启用避雷规则；用户仍可编辑，但不应从空白开始。

### P0-05 理发记录流程违背真实场景

当前要求六类照片：剪前、理发中、未造型、已造型、洗后、第 7 天。用户不会在剪发中操作手机，也不应为了使用应用而拍摄一套研究样本。

新流程只需要：

- 剪前照片；
- 剪后照片。

旧阶段继续兼容读取，但不再出现在新记录主流程，也不再触发首页补录任务。

### P0-06 记录表单在手机上严重挤压

两列输入、两列结果选项和六个文件控件造成视觉折叠。原生文件按钮显示英文，文件名被截断，重要字段没有主次。

**必须改为单列渐进表单：**首屏只放剪前/剪后、日期、发型名、满意度与“下次是否想复刻”；店铺等低频信息放入“补充本次信息”。文件控件使用中文自定义按钮和大图预览。

### P0-07 满意度和复刻状态存在诱导性默认值

新记录默认 5/5，结果默认“复刻”。用户即使没有认真选择，也会制造一条满分可复刻记录，继而生成错误的标准发型。

满意度必须默认未选择；完成基础记录后再问“下次还想这样剪吗？”，选项应是“想复刻 / 有些地方要调整”，而不是先替用户决定。

### P0-08 没有剪前/剪后照片墙和直观比较

记录详情按阶段纵向展示单张大图；档案总览也没有照片时间线。用户无法快速回答“这次和之前到底差在哪”“哪次最好看”。

至少提供：同尺寸剪前/剪后对比、最近三次剪后缩略图、标准发型照片、避雷记录入口。照片墙是个性化感的主要来源，不是装饰。

### P0-09 店铺位置缺失

只有店铺名称，没有分店、商场、街道或地址，无法支持下次复刻。第一阶段不需要地图接口，增加可选的纯文本“店铺位置”即可，记录详情显示店铺、位置、理发师。

### P0-10 固定底栏与页面操作坞叠加、遮挡内容

发型详情、私人参考详情、沟通卡编辑等页面同时出现全局底栏和页面级固定操作坞。截图中正文、标签、预览和保存区域被横切；私人参考详情甚至把五个不同权重的动作挤进同一条浮层。

沉浸任务应隐藏全局导航；普通页面最多保留一个固定层。删除不应和“加入计划、给理发师看、收藏”处于同等显著位置。

### P0-11 理发师展示不是理发现场工具

精选“给理发师看”长达两千多像素，沟通要点、最在意、绝对不要需要持续滚动。缺少：

- 一屏关键点模式；
- 图片点击放大；
- 屏幕常亮；
- 临时手写或圈点标注；
- 明确的正面/侧面/后脑图片边界。

它现在更像文章详情，不像用户坐在理发椅上递给理发师的工具。

### P0-12 新旧视觉系统冲突，不能继续靠覆盖 CSS 修补

首页和精选库使用浅色图标、圆角与轻材质；计划、记录、沟通卡仍有粗黑分隔、黑块标题、原生控件和模板式英文眉题；遮罩编辑器又突然变成黑色工作台。

三份主样式约 6,892 行且 selector 重叠。应逐条核心路径重构信息结构并删除旧规则，不能再加一层 `!important` 或全局覆盖。

### P0-13 本机数据没有可恢复出口

本机保存符合当前不做账号的策略，但照片墙、理发历史和标准发型一旦被清缓存或换机就会全部丢失。对一次性演示可接受，对真实长期使用不可接受。

低成本方案是在不做账号的前提下提供本地导出/导入包，并明确包含什么、不包含什么、是否加密。此项会扩展旧阶段边界，但若要开放真实用户，必须重新评估，不能只用风险文案替代恢复能力。

### P0-14 卡片、按钮和手势没有形成统一的“可触摸物理系统”

用户补充的问题成立，但需要精确定义：**不是把所有内容都装进浮起的大卡片，而是凡被设计为卡片的交互对象，都必须有可信的体积、边界和状态；凡被设计为按钮的控件，都必须一眼看出可以按，并在触摸全过程持续反馈。**

当前已经有局部 `v-tactile` 按压基础和筛选轨道拖动逻辑，这是正确方向；问题是覆盖范围太窄，且没有形成全产品规范：

- 档案、计划、记录、沟通卡中的大量文字链接和矩形色块不像按钮；
- 多数卡片只有白底、圆角和浅阴影，没有前后层级、受光边缘或按压时的阴影变化；
- 一些可点击整卡和普通信息卡外观相同，用户无法预判能否操作；
- 候选目前不能通过真实拖动排序；收藏移动主要依靠下拉框；
- 按下反馈只覆盖部分页面，松手后的回弹、取消、拖出后恢复没有统一视觉语言；
- 页面切换有通用淡入，但没有从触发按钮或卡片位置产生的空间连续性。

**整改原则：**

1. **先区分三类表面。** 普通信息区尽量无卡片；可点击卡片有清楚边界、轻微浮起和方向提示；浮动工具条/sheet 才使用玻璃材质和更明显深度。
2. **按钮必须像按钮。** 主按钮使用实色填充、稳定高度、图标与文字；次按钮使用浅色实体或清晰描边；文字链接只用于低权重导航，不能冒充主要操作。
3. **触摸按下立即响应。** `pointerdown` 后一帧内出现轻微压缩、阴影收紧和高光变化，不等待业务请求或 `click`。
4. **拖动必须 1:1 跟手。** 候选排序、照片调整、横向内容轨道、sheet 等真实可拖对象要保持抓取点，不突然吸到中心；超过边界时使用渐进阻力。
5. **松手传递速度并可中断。** 有效落点使用克制弹簧吸附；无效落点回到原位；运动中重新触摸可立即接管，不能等动画结束。
6. **允许取消。** 按住后拖出按钮约 10px 容错范围应取消提交，拖回后重新激活；危险操作不应在按下瞬间执行。
7. **动效服从无障碍。** 减少动态时移除弹跳和大位移，用颜色、明暗、轮廓或短淡变保留状态反馈。

这项不是“后期润色”。在移动端，视觉体积与连续反馈共同告诉用户哪里能按、按下是否生效、对象是否正在跟随手指，因此属于核心可用性和品质门槛。

## 6. 全页面逐页问题矩阵

下表覆盖全部可到达路由；同一组件的新建/编辑状态分别列出，因为用户任务和风险不同。

| 路径 / 页面 | 用户真实任务 | 当前主要问题 | 严重度 | 建议方向 |
| --- | --- | --- | --- | --- |
| `/` 首页 | 看懂产品、知道下一步 | 62px 级标题抢占首屏；主视觉是固定示例；建档后仍不像“我的首页”；隐私说明重复 | P1 | 有档案后优先展示我的当前照片、最近剪后和唯一下一步 |
| `/try` 示例试发型 | 理解某款大致方向 | 隐藏于主导航但仍可直达；与精选库重复；固定三个人物、两方案容易被理解成真正试发型 | P1 | 退役或改名“示例方向对比”，不要与真实候选流程并存 |

### 不存在资源的状态

私人参考、计划、记录和沟通卡在 ID 不存在时都给出了诚实终态，没有自动拿第一条数据替代。这是正确的，应保留。问题在于这些终态页面仍沿用夸张标题和过多空白，恢复入口也不够一致。

## 7. 跨页面产品闭环问题

### 7.1 发现发型到建立计划有重复入口

用户可以在精选库看发型，也可以在计划表单里再次浏览六个预设，还存在单独的 `/try` 示例页。三个入口都在做“发现方向”，但内容、术语与结果不同。

建议只保留一个权威发型库；精选、私人参考、历史记录都从那里加入计划。计划页不再内嵌第二套发型库。

### 7.2 计划不是对比工具

2–4 个候选纵向排列，用户需要记住上方图片再向下对比。移动端更适合左右滑动、固定同一信息结构、快速标记“更喜欢/待确认/排除”，而不是长文章式浏览。

### 7.3 沟通卡没有利用已有知识

用户已经在发型详情、档案备注、避雷历史中表达过信息，却要在沟通卡再次填写。产品没有减少用户表达成本，这是“数据存了但没有服务用户”的典型问题。

### 7.4 记录完成后没有形成视觉记忆

记录会生成标准发型或避雷规则，但档案首页不展示剪前/剪后成果，也没有“过去最好的一次”。用户第二次回来仍要读文字，而不是看自己。

### 7.5 本机保存的价值与风险不平衡

本地优先带来隐私优势，但长期数据价值越高，丢失风险越不可接受。目前多页重复警告“清理浏览器会丢失”，却不给用户恢复出口。风险提示不能代替风险控制。

## 8. 信息架构与文案问题

### P1-01 页面围绕数据表命名，而不是用户任务

“本机主档案、发型计划、剪后记录、标准发型、沟通卡”是系统概念。用户更关心：“我现在什么样”“下次想剪什么”“给理发师看什么”“哪次值得复刻”。

### P1-02 技术和内部状态词过多

`LOCAL ONLY`、`PLAN DETAIL`、`CUT RESULT`、`草稿`、`ready` 对普通用户没有帮助。中英文 eyebrow 和编号更像设计模板，不像私人工具。

### P1-03 空状态堆叠放大“产品什么都没有”

档案总览一次展示多个“还没有”，让新用户感觉要完成六项工作才能开始。应只展示当下一个任务，其余用完成后示例或渐进解锁表达。

### P1-04 隐私说明重复且压过价值

隐私边界必须诚实，但当前多页用大卡反复说明本机存储。建议首次上传完整说明，后续只显示一行“仅存本机”，详情可展开。

### P1-05 删除使用浏览器原生确认框

原生 `confirm` 与应用视觉割裂，且无法清楚展示将删除哪些照片、记录和衍生内容。重要删除应使用应用内确认 sheet，明确不可恢复范围。

## 9. 视觉与交互系统问题

### 9.1 层级比例失衡

- 首页 62.4px、部分页面 54.6px 的标题吞掉首屏；
- 底栏、候选按钮和文件控件却只有约 10–12px；
- 照片本应是产品主角，但常被标题、说明卡和固定导航挤压。

### 9.2 Apple 风格只停留在表面

Apple 式体验的核心不是更多透明和圆角，而是即时反馈、直接操作、可预测、克制和空间连续性。当前动画多为通用缩放；候选加入、收藏移动、图片替换、保存成功、拖动排序没有形成清楚的因果反馈。

### 9.3 颜色语义不稳定

蓝色、紫色、黑色、珊瑚色都在承担主操作或状态。危险删除有时只是文字链接，有时与主动作同列。应建立稳定语义：品牌、主动作、成功、提醒、危险各有唯一角色。

### 9.4 卡片和边框过量

档案、计划、记录仍依靠大卡、黑线和网格切分。每块都被强调，反而没有重点。照片流与长表单尤其不适合“卡片套卡片”。

### 9.5 没有针对全产品验证 200% 字体

精选库已有相关证据，但档案、记录和沟通卡的双列/固定层结构更危险。不能用“没有横向滚动”代表可用；文字被压成窄列、按钮被遮挡同样是不通过。

### 9.6 固定层没有统一规则

底部导航、详情操作坞、沟通卡导出条分别独立实现，缺少“每页最多一个固定层”的全局约束。这也是多页遮挡反复出现的根因。

### 9.7 卡片体积缺少统一层级

当前卡片常见两种极端：旧页面使用粗边框和硬黑块，新页面使用几乎完全平的白色圆角。二者都没有稳定表达“这是背景分区、可点击对象，还是浮在内容上方的工具”。

建议只设三层材料：

- **内容层**：照片、正文、列表直接落在白色或极浅灰背景上，不强行加卡；
- **交互卡片层**：轻微外阴影、1px 受光边缘、明确圆角和按压时的高度变化；
- **浮动控制层**：导航、操作坞、sheet 使用白色半透明材质、背景模糊和更深阴影。

体积感来自光、边界、遮挡关系和交互状态，不是把阴影调得更黑。所有卡片都浮起来会失去层级，因此普通说明区必须保持平静。

### 9.8 缺少全产品动作状态表

每个交互组件至少需要定义：默认、按下、拖出取消、拖回、禁用、加载、成功、错误和减少动态状态。推荐的体验基线：

| 动作 | 应有反馈 |
| --- | --- |
| 按下按钮 | 立即压缩约 2%–4%，阴影收紧，高光向触点聚拢 |
| 手指停留 | 保持压下状态，不提前执行动作 |
| 拖出按钮 | 解除压下状态并取消提交意图 |
| 拖回按钮 | 恢复压下状态，松手才提交 |
| 松手提交 | 从当前显示状态回弹，重要保存同时显示明确完成状态 |
| 拖动卡片 | 1:1 跟手、抬高一层、原位显示占位，滚动与拖动意图可区分 |
| 有效松手 | 携带松手速度进入目标位置并克制回弹 |
| 无效松手 | 原路径返回，不能瞬移或直接消失 |
| 中断动画 | 新触摸从当前屏幕位置接管，不跳到旧目标 |
| 减少动态 | 取消弹簧、惯性和大位移，用颜色/轮廓/短淡变反馈 |

不要为每个页面各写一套手感。应建立可复用的 Button、IconButton、TactileCard、DragRail、SortableItem、ActionSheet 和 Dock 交互原语，再逐页采用。

## 10. 当前值得保留的能力

审计不是全盘否定。以下能力已经具备真实价值，应在重构中保留：

- 图片在浏览器本地纠正方向、压缩、重绘和去 EXIF；
- 私人参考、档案原图不上传；
- MediaPipe 同源运行，失败可手动遮罩，多人照片硬拦截；
- 私人参考新增、编辑、收藏、文件夹和给理发师看均为真实本地功能；
- 精选发型详情包含现实可剪性、维护成本和完整沟通要点，不只展示好看照片；
- 计划能混合精选、私人参考和真实历史照片，并保存快照；
- 沟通卡可导出 PNG 和打印；
- 记录可形成复刻或避雷的结构化结果；
- 存储失败、图片处理失败和资源不存在状态普遍诚实且可恢复；
- 没有社区、评论、点赞、公开投稿和社交排行榜，符合最新产品边界。

这些能力说明问题不是“从零重做技术”，而是需要重新组织用户旅程和视觉优先级。

## 11. 推荐目标产品：个人发型护照

### 11.1 首次建立

改为三个短步骤：

1. **我现在的头发**：正面照片建议上传，侧面/后脑可选；
2. **我想呈现的感觉**：称呼、性别资料、发型呈现偏好；
3. **真实头发条件**：发质、粗细、发量、打理时间，以及易贴、易炸、发旋、发际线等高信号选项。

不确定项默认“暂不确定”，不能提前替用户选中答案。

### 11.2 我的档案首页

首屏只回答：

- 我现在是什么状态；
- 下一步要做什么；
- 上次哪里值得复刻、哪里必须避开。

建议结构：当前照片/最近剪后照片拼贴、个人摘要、唯一主行动、剪前/剪后时间轴、标准发型和避雷。计划与沟通卡作为二级入口。

### 11.3 发型库个性化

使用本地、可解释规则：发质、发丝粗细、打理时间、呈现偏好和维护接受度参与排序。每款输出 2–3 条适合原因和一条现实取舍；允许关闭“为我排序”。

### 11.4 理发记录

第一屏只保留：剪前照片、剪后照片、日期、发型名、满意度和“下次是否想复刻”。店铺、位置、理发师、服务、价格、耗时、备注折叠在“补充本次信息”。

### 11.5 理发师模式

一屏显示目标图、整体方向、三个最在意、三个绝对不要；向下才是分区细节。支持点击图片放大、屏幕常亮和临时圈点，不修改原始档案。

### 11.6 统一的交互质感

目标风格应是“简约白色系统界面 + 不同功能的彩色小图标 + 可信的浅层体积”。照片仍是最强视觉锚点，卡片和玻璃只承担交互层级。

核心交互记忆点控制在三类：

1. **按压**：按钮和可点击卡片在触摸落下时立即压低，松手回弹；
2. **拖动**：候选排序、筛选轨道和可移动对象连续跟手，边缘有阻力；
3. **归位**：收藏、加入计划、照片替换等完成后，从触发位置连续过渡到新状态，而不是突然刷新整页。

这三类行为应贯穿首页、发型库、档案、计划、记录和沟通卡，而不是只存在于少数展示页。

## 12. 推荐整改顺序

### 阶段 A：修阻断与数据模型

1. 立即修复记录结果白字白底；
2. 档案增加照片、性别资料、呈现偏好和高信号头发条件；
3. 记录模型简化为剪前/剪后，旧六阶段只兼容读取；
4. 增加店铺位置纯文本；
5. 去除满意度/复刻默认值；
6. 移除首页洗后/第 7 天补录任务。

### 阶段 B：重建核心闭环

1. 照片化的个人档案首页；
2. 发型库本地个性化排序和解释；
3. 精选指南、档案偏好、避雷规则自动汇入沟通卡；
4. 候选真实对比与主方案确认；
5. 剪前/剪后详情与照片时间轴；
6. 理发师一屏模式。

### 阶段 C：逐页视觉重构

1. 先档案、记录、计划、沟通卡，再遮罩与我的；
2. 每重构一条路径就删除对应旧 selector，不继续叠覆盖；
3. 统一标题、正文、按钮、图标、状态色和固定层规则；
4. 建立 Button、IconButton、TactileCard、DragRail、SortableItem、ActionSheet、Dock 的统一体积和状态规范；
5. 动效只服务于按下、拖动、松开、加入、替换、保存和撤销的因果反馈；
6. 每页完成真实 360/390/430 和 200% 字体验收。

### 阶段 D：公开体验前保障

1. 本地数据导出/导入或明确替代方案；
2. 全页面错误、存储不足、无痕模式和图片失败状态；
3. iOS Safari、Android Chrome、微信内置浏览器实机；
4. 完整新用户与回访用户走查，而不是只跑技术测试。

## 13. 发布验收标准

### 产品

- 建档后首屏出现用户照片或明确照片空位，不能只有文字；
- 性别资料、呈现偏好和头发条件可自定义且刷新保留；
- 至少三款精选会因档案改变排序或解释；
- 沟通卡能继承候选指南、档案偏好和启用中的避雷规则；
- 新记录只有剪前/剪后两个主照片入口；
- 新记录不再出现洗后/第 7 天任务；
- 满意度和复刻状态无默认答案；
- 店铺位置可保存、编辑、展示；
- 历史六阶段照片不丢失。

### 移动端

- 360 × 800、390 × 844、430 × 932 无溢出、遮挡或窄列折叠；
- 手机表单不再出现约 156px 双列文字输入或约 135px 原生文件控件；
- 任一页面最多一个固定层；
- 关键正文不低于 15px，辅助文字不低于 12px，触控目标至少 44 × 44px；
- 记录结果、错误、成功、危险操作满足稳定对比度；
- 200% 字体、减少动态、减少透明度下仍能完整操作；
- 所有主要按钮一眼可识别为按钮；文字链接不承担主要提交动作；
- 所有交互卡片和普通信息区可仅凭外观区分；卡片按下时阴影与高度同步变化；
- 按下反馈在下一帧出现，按住不提前提交，拖出可取消，拖回可恢复；
- 可拖对象 1:1 跟手、保留抓取偏移，有效松手归位、无效松手原路返回，动画可被重新触摸中断；
- 减少动态时不使用弹簧、惯性或大位移，但仍保留颜色、轮廓和完成反馈；
- 按下、拖动、松开和保存反馈可感知，不造成误触、等待或滚动冲突。

### 真实场景

- 用户在一分钟内建立最小档案；
- 用户在理发后一分钟内完成剪前/剪后记录；
- 用户能在理发椅上不滚动或极少滚动地把关键要求给理发师看；
- 第二次打开应用时，能立即看到自己的照片、上次结果和下一步；
- 清缓存风险被明确说明，并有可执行的恢复/导出方案。

## 14. 本轮明确不扩展

- 不做社区、帖子、评论、点赞、公开投稿；
- 不做账号、云同步、微信/手机号登录；
- 不做地图服务和定位权限，位置先用纯文本；
- 不做真实 AI 试剪或远程人脸分析；
- 不做支付、会员、积分、订单或兑换码页面；
- 不做理发师端或商家后台；
- 不用更多毛玻璃、阴影和动画掩盖信息架构问题。

## 15. 最终产品判断

用户指出的问题全部成立，而且问题远不止那四页。当前产品已经证明“这些功能技术上可以做”，但还没有证明“普通人愿意持续用”。

下一轮不能以“把档案页美化一下”为目标。正确目标是：

> 第一次建档，我能看到自己的头发；第二次理发，我能直观看到剪前和剪后的差异；第三次回来，应用能根据我的真实条件告诉我什么更适合、上次哪里值得复刻、哪里必须避开，并让我一屏把要求说给理发师听。

做到这一点，白色、彩色小图标、毛玻璃和细腻动效才会成为产品体验；否则它们只是一层漂亮外壳。

## 16. 三套 Skill 交叉复审补充

### 16.1 使用方法与证据边界

本轮不是重新换一种语气评价同一批截图，而是使用三套不同方法回答三个问题：

1. **Product Manager Skills**：使用 `jobs-to-be-done` 与 `customer-journey-map`，检查用户到底雇用这款产品完成什么任务，以及价值在旅程的哪个交接点丢失；
2. **OpenAI Product Design**：使用 `audit` 框架检查价值主张、视觉层级、交互可供性、错误状态、无障碍和设计系统一致性；
3. **Playwright Interactive**：按 QA inventory 重新执行真实浏览器旅程，分别检查功能、视觉、触控状态与视口适配。

当前基线重新运行了 23 个 Playwright 场景，结果为 23/23 通过；同一次运行生成 42 张当前截图，随后又以 390 × 844 视口探索 12 个代表性入口并生成 12 张截图。检查包含首页、发型库、收藏、私人参考、档案、建档、计划、沟通卡、记录、隐私遮罩、我的和 404，也覆盖有数据、无数据、处理中、存储失败、资源缺失及真实 MediaPipe 状态。

这份报告不把浏览器测试通过等同于产品通过。当前 `record-detail-390x844.png` 仍稳定呈现近白字叠白底的结果卡，说明“测试生成了截图”不等于“截图经过了设计验收”。

边界说明：以下 JTBD、人物动机和旅程痛点来自当前需求、代码、页面与截图，是**待真实用户访谈验证的产品假设**；本轮没有理发店现场观察、真实用户访谈、行为分析数据，也不宣称完成完整 WCAG 合规审计。

### 16.2 应当服务的核心 Job

#### 功能任务

> 当我不知道剪什么、又担心理发师理解错时，我想把自己当前的头发状态、喜欢的参考和过去真实结果变成一个现实可剪的方案，并在理发现场快速说清楚；剪完以后，我希望记住这次哪里成功、哪里失败，让下一次少翻车。

#### 情绪任务

- 在进理发店前降低不确定感，而不是让我先完成一套资料录入；
- 看到“这是基于我的照片、头发条件和历史给出的答案”，而不是通用短发文章；
- 对隐私和数据丢失风险有清楚预期，但隐私说明不能盖过产品价值；
- 剪完以后感觉自己积累了可复用经验，而不是多维护一条数据库记录。

#### 社交任务

- 在理发师面前显得准备充分、要求明确，而不是一边翻长页面一边临时组织语言；
- 能够自然地表达“最在意什么”和“绝对不要什么”，避免被认为含糊或难沟通；
- 不因一次失败发型在工作、约会或社交场景中持续付出代价。

当前产品的主要错位是：它把用户任务理解成“管理档案、计划、沟通卡和记录”，而用户真正购买的是“更快做出决定、在现场说清楚、下次记得住”。

### 16.4 新增 P0 发现

#### S-P0-01 激活路径倒置：先收资料，后给价值

新用户首页的唯一主动作是“建立我的头发档案”，而档案保存后不会立即产生个性化排序、专属解释、照片护照或沟通卡草稿。用户先承担填写成本，却看不到“填写这些以后有什么不同”。

产品上应改成**先给一小步可感知结果，再逐步补资料**：例如先选一张当前头发照片或三项关键条件，立刻看到“更可能适合/需要谨慎”的精选分组和原因；其余资料在用户准备计划时再补。首个个性化结果应在首次使用 60 秒内出现。

#### S-P0-02 档案把稳定特征和当前状态混在一起，但实际上两者完全不同

当前 `HairProfile` 只有称呼、发质、发丝粗细、发量、打理分钟、洗发频率和备注。这些大多是相对稳定的条件，却缺少真正影响“今天能不能剪”的当前状态：当前长度、正面/侧面/后脑照片、距上次剪发时间、近期烫染、正在留长的区域、当下最困扰的问题。

因此即使把现有文字做得更漂亮，也仍然无法让用户感到量身定制。应把数据拆成：

- **我的稳定条件**：发质、发丝、发量、打理能力、风格呈现偏好；
- **我现在的头发**：当前照片、长度、最近处理、正在留长区域、当前困扰；
- **我已验证的经验**：复刻点、避雷点、实际维护成本。

性别资料也不应直接等于推荐逻辑。应同时支持用户自定义性别/不愿透露，以及独立的“我想呈现的风格”偏好；真正用于发型筛选的是后者和头发条件，不是用男性/女性做粗暴限制。

#### S-P0-03 已经拥有个性化数据，却在界面层被闲置

精选目录的数据模型已有 `genderPresentation`、`hairTextures`、`strandThicknesses`，筛选函数也支持 `hairTextures`；但当前发型库界面只提供“我更在意”和“日常维护”，没有把用户档案接进筛选，也没有说明“为什么适合你/为什么不建议你”。

这是比“推荐算法还不够聪明”更基础的问题：不是缺数据，而是现有数据没有参与用户决策。首阶段甚至不需要 AI，只要做透明的规则匹配，也能产出可信的个性化解释。

#### S-P0-04 计划增加了候选数量，却没有帮助用户做决定

探索计划允许 2—4 个候选，但计划页面本质上仍是图片与来源的集合。用户因为“不知道剪什么”而来，最后只是从不知道选一个，变成不知道在四个里选哪一个。

至少需要一个明确的决策面板：每款对本人的匹配原因、现实风险、日常打理、必须保留的长度、需要向理发师确认的问题，并允许标记“主方案/备选/排除原因”。沟通卡不应承担第一次决策，它只应承接已经确认的主方案。

#### S-P0-05 关键交接点要求用户重复输入，个性化知识没有流动

当前沟通卡新建时只默认选择第一个候选，其余整体、顶部、刘海、两侧、后脑、最在意和绝对不要均为空；精选详情里的理发指南、档案偏好和历史避雷不会自动进入。剪后记录即使通过 `planId` 进入，也只预选计划，不会自动带入发型名、目标候选、店铺或待验证要点。

这会让用户在“收藏 → 计划 → 沟通卡 → 记录”每一步重新解释自己。正确体验应是同一份知识逐步被确认和修正：

- 精选/私人参考带入候选；
- 主候选与本人规则生成可编辑沟通卡草稿；
- 理发记录继承计划、主方案和待验证项；
- 结果再反向更新标准发型和避雷规则。

#### S-P0-06 剪后学习模型太粗，无法回答“为什么翻车”

现有结果只有一个满意度总分，以及“复刻/避雷”二选一。真实结果往往是混合的：轮廓适合但剪短了、理发师执行好但自己不会打理、当天造型好看但洗后失效、发型没问题但维护时间不可接受。

若不区分原因，低分无法指导下一次，高分也不知道该复制什么。建议保留轻量输入，但至少拆出四个可选判断：

- 适不适合我；
- 理发师是否按要求执行；
- 自己是否容易打理；
- 哪一处保留、哪一处调整。

“复刻/避雷”应成为总结，不应强迫用户把一次复杂体验压成黑白答案。

#### S-P0-07 浏览器测试通过，但视觉缺陷没有成为发布门禁

本轮 23/23 Playwright 通过，同时真实截图仍出现近白字叠白底、固定操作层叠加、长计划页信息失衡等明显问题。当前 E2E 会调用 `page.screenshot()` 留图，但没有 `toHaveScreenshot` 视觉基线，也没有一张张人工签字的 Design QA 清单。

因此发布流程实际证明的是“路径可走通”，没有证明“人在当前状态下看得清、知道点哪里、愿意继续”。后续每个核心旅程必须同时有三道独立门：

1. 功能结果正确；
2. 390/430/200% 字体下布局可用；
3. 关键状态截图经过 Product Design 人工验收或稳定视觉基线比较。

### 16.5 新增 P1 发现

#### S-P1-01 六款正面示例不足以解决“发型知识盲区”

六款精选足够证明目录、收藏和加入计划可以工作，但不足以作为面向真实用户的发型库。用户需要看到同一发型的正面、侧面、后脑、未造型状态、适合长度区间和维护成本；只有正面人物图容易让人把脸部气质误认为发型适配。

上线前应先做“内容覆盖矩阵”，不是盲目追求数量：不同风格呈现、发质、发量、眼镜、发际线、维护能力和长度目标都要有最小覆盖；每条内容必须有现实限制和理发师沟通要点。

#### S-P1-02 理发师是关键次级用户，但当前没有真正参与验证

沟通卡和“给理发师看”页面是本产品差异化最强的部分，却仍主要按创建者视角组织。应至少找 3—5 位真实理发师完成现场任务：在 5—10 秒内看懂目标、指出不可剪原因、确认长度边界，并观察是否需要放大、横屏、锁屏常亮或离线重开。没有这一步，“一屏沟通”仍只是内部假设。

#### S-P1-03 当前没有定义可验证的产品成功指标

在不做经营数据和侵入式埋点的前提下，也应为可用性测试定义任务指标：

- 首次个性化结果出现时间；
- 从收藏到确定主方案的完成率；
- 理发现场 10 秒内找出“最在意/绝对不要”的成功率；
- 剪后 60 秒内完成前后记录的成功率；
- 第二次理发时成功复用标准发型或避雷规则的比例。

这些指标可以先在小规模人工测试中记录，不要求现在建设账号、后台或经营看板。

### 16.6 三条必须通过的用户故事

#### 用户故事 A：第一次使用

> 作为一个不知道剪什么的用户，我希望在 60 秒内提交最少信息后，看到至少三款与我当前条件相关的候选、匹配原因和风险，而不是先填写一份通用档案。

验收：无需账号；可以稍后补资料；推荐结果明确说明规则来源；没有用户条件时不冒充个性化。

#### 用户故事 B：理发现场

> 作为坐在理发椅上的用户，我希望一屏向理发师展示目标图、三项最在意、三项绝对不要和关键长度边界，不需要在长表单中滚动寻找。

验收：5—10 秒可读；离线重开可用；无固定底栏遮挡；照片和文字均可放大；不把正面图冒充完整侧后参考。

#### 用户故事 C：第二次理发

> 作为回访用户，我希望马上看到上次剪前/剪后对比、成功点、失败点、店铺位置和可复刻方案，并能基于上次结果开始新计划。

验收：不要求补洗后/第 7 天照片才能继续；历史六阶段照片不丢失；新记录默认只要求剪前和剪后；复刻计划能继承已验证信息。

### 16.7 修订后的优先级

1. **立即阻断**：修复结果卡不可读、固定层遮挡、记录表单挤压和默认答案；
2. **核心产品重构**：建立“当前头发 + 稳定条件 + 已验证经验”的个人发型护照，提供剪前/剪后照片墙；
3. **打通知识流**：档案与精选参与个性化解释，候选帮助收敛，沟通卡与记录自动继承；
4. **精简真实任务**：新记录只要求剪前/剪后，增加店铺位置，复刻/避雷不再默认；
5. **统一全产品设计系统**：卡片体积、按钮可供性、按压/拖动/松手、固定层和减少动态统一覆盖，而不是只在首页与发型库生效；
6. **建立 Design QA 门禁**：功能、视觉、可访问性和真实用户任务分别验收；
7. **最后才扩大内容与开放体验**：发型库覆盖矩阵、理发师现场测试和小规模真实用户测试通过后，再考虑陌生用户或收费。

### 16.8 交叉复审结论

三套 Skill 得出的结论一致：当前版本最大的风险不是“功能少”，而是**用户付出了大量录入和选择成本，产品却没有把这些数据变成更确定的决定、更短的沟通和更清晰的下一次经验**。

因此下一轮不能以“全面美化 23 个页面”为起点，也不能先增加更多发型或动画。应先重做一条纵向闭环：

> 当前头发与偏好 → 个性化候选解释 → 主方案收敛 → 一屏沟通 → 剪前/剪后记录 → 下次可复用经验。

这条闭环通过真实用户和理发师验证后，再把统一的白色 Apple 风格、彩色小图标、卡片体积和物理动效扩展到全产品，才不会继续出现“技术完成、视觉也做了，但真实用户仍然不知道为什么要用”的问题。
