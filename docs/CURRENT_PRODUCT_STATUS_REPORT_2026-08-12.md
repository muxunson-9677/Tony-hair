# 「咋剪发」当前方案与 V3 重构进度汇报

> 更新时间：2026-08-12  
> 汇报对象：产品、设计、工程或外部 AI 评审者  
> 当前业务实现基线：`b39ab584bc96c6d8f92cc817f0c4d7cc2c71a2a7`

## 1. 一句话结论

「咋剪发」已经不是静态 UI 演示，而是一套可以在浏览器本机完成“找方向 → 建计划 → 给理发师看 → 记录剪前/剪后 → 复刻或避雷”的真实本地闭环。

当前最重要的缺口不是继续增加页面，而是让历史记录真正自动影响下一次决策，并补齐离线现场、外部分享文件和未来真实 AI 的质量边界。

## 2. 产品当前定位

### 核心目标

降低真实理发翻车概率，让用户每次理发不再从零开始。

### 核心用户

- 18 岁以上、男女均可使用的短发用户；
- 不清楚自己适合什么、不会向理发师表达的人；
- 曾经剪成功或剪失败，希望下次能复刻或避雷的人。

### 核心闭环

```text
个人头发档案
→ 从精选发型、私人参考图或历史记录中找方向
→ 建立探索计划或复刻计划
→ 生成理发师沟通卡与现场展示页
→ 记录剪前/剪后照片、店铺位置和满意度
→ 保存为“下次照着剪 / 下次微调 / 下次避开”
→ 为下一次理发提供依据
```

### 明确不做或当前搁置

- 永久取消：社区、发帖、评论、点赞、关注、私信、公开主页、站内好友投票；
- 不做：应用内支付、订单、会员、积分、兑换码、客服台、经营后台；外部权益和发码交给外部平台；
- 暂不做：微信登录、手机号登录、理发师端、商家端、AR；
- 邮箱六位验证码登录只保留未来占位，不阻塞游客使用本地功能；
- M4 与 M7 按当前产品决定搁置，除非产品负责人以后重新启动；
- 当前不扩充大规模发型素材库，先用 6 款精选验证业务逻辑。

## 4. 已实现能力

### 4.1 本地个人档案

- 性别支持“女 / 男 / 不透露”，并支持呈现偏好；
- 头发档案可保存照片、发质、粗细、发量、打理时间、洗发频率和个人备注；
- 档案首页以照片和历史内容形成个人感，不再只有通用文字；
- 所有档案和图片默认保存在当前浏览器 IndexedDB/Dexie 中；
- 已有本地数据导出、导入与删除能力；
- 界面明确说明清理浏览器数据、无痕模式或换设备可能丢失。

### 4.2 发型发现与私人参考

- 6 款精选发型，支持搜索、目标筛选和维护难度筛选；
- 支持收藏夹创建、改名、移动和删除；
- 支持上传自己的发型参考图并长期保存；
- 图片写入前在本地纠正方向、限制长边、压缩、Canvas 重绘和清除 EXIF；
- 私人参考图可添加名称、备注和重点区域；
- 精选和私人参考均有“给理发师看”模式；
- 私人图失败、重复、存储不足、异步竞态和 Object URL 回收已有测试保护。

### 4.3 理发计划

- 探索计划：支持 2–4 个候选方案；
- 复刻计划：支持 1 个标准发型或历史来源；
- 候选可来自精选示例、私人参考图或历史记录；
- 计划保存的是独立快照，即使后来删除原始参考图，计划和沟通卡仍可用；
- 支持主方案、候选比较和计划详情；
- 删除档案/计划时会保护仍需恢复的历史数据，避免留下不可发现的本机孤儿状态。

### 4.4 理发师沟通卡与现场模式

- 包含目标图、整体要求、顶部、刘海、两侧、鬓角、后脑；
- 支持“最在意三项”和“绝对不要三项”；
- 支持区域参考图与局部沟通；
- 支持 PNG 导出和打印；
- 现场页隐藏普通 App 外壳，优先展示照片、大字和关键要求；
- 私人参考只展示用户自己的备注，不伪造 AI 推断；
- 精选示例明确披露是示例，不冒充用户本人的 AI 结果。

### 4.5 剪后记录与个人记忆

- 当前主流程只要求剪前和剪后照片，不要求用户理发中操作手机；
- 支持店铺名称、店铺位置、理发师、价格、耗时和备注；
- 支持满意度；
- 支持“下次照着剪 / 下次微调 / 下次避开”；
- 可由满意记录形成标准发型，由失败记录形成避雷规则；
- 历史照片和记录在刷新后仍可恢复；
- 旧版更多照片阶段仍兼容读取，但不再作为新记录主流程的负担。

### 4.6 本地隐私遮罩

- MediaPipe Face Landmarker 在浏览器 Worker 中运行；
- 模型与 WASM 资产同源固定版本并校验哈希；
- 单人可自动定位，失败可切换手动模式；
- 多人照片硬拦截，避免错误遮罩后继续分享；
- 支持拖动、缩放、旋转和三种不透明样式；
- 导出时照片与遮罩在 Canvas 中扁平化；
- 原图、关键点和编辑图层不通过网络发送；
- 支持减少透明度、减少动态效果和不支持 `backdrop-filter` 时的实色回退。

### 4.7 Apple 式轻量体验重构

- 移动端优先，已验证 360 / 390 / 430px 和桌面预览；
- 视觉采用白色、浅灰和多色小图标，不采用深色大面积毛玻璃；
- 毛玻璃只用于导航、操作坞和短暂浮层，不铺满正文；
- 卡片有层级、边界、阴影和体积感；按钮保持明显可按；
- 已有统一 `v-tactile` 触感：按下立即反馈、拖出取消、松开回弹；
- 触控目标约 45px，支持键盘焦点、200% 字体、减少动态和高对比偏好；
- 任务页减少底部导航干扰，首页只给一个当前最值得做的动作；
- 开发术语和英文状态标签已大幅改为用户能理解的中文。

## 5. 重构方案完成情况

### 已完成或大部分完成

- 三个自然语言入口：“帮我选 / 我有参考 / 照上次剪”；
- 首页从功能宫格转为单一下一步；
- 第一次建档渐进披露，不强迫用户一次填完；
- 发型计划区分探索与复刻；
- 沟通卡和现场模式成为核心结果，而不是附属页面；
- 剪后记录压缩为约 60 秒的必要输入；
- 用户照片、历史记录和标准发型形成个人档案；
- 参考图重点区域交互；
- 统一按钮、卡片、操作坞和按压/拖动/松开反馈；
- 空状态、加载、错误、存储失败、无障碍和隐私状态有系统测试；
- 社区、投票和商业后台从前台产品中移除。

### 部分完成

- “它真的记得我”：已经能保存历史，但历史还没有充分自动改写下一次计划；
- 现实可剪性：已有静态说明和沟通字段，但不是根据用户当前长度、发旋、发际线等动态计算；
- 对象连续性：局部页面有稳定照片/快照和轻动效，但还没有系统级 shared-element 过渡；
- Undo：部分操作有确认和恢复语义，但没有统一的短时撤销系统；
- 理发现场兜底：可导出图片，但 H5 还没有完整 PWA/service worker 离线重开保证；
- 分享：沟通卡和遮罩图可导出，统一的对比图、复盘图和系统分享工作室尚未完成。

### 未实现

- 真实 AI 发型生成、真实本人试剪和真实模型接入；
- 用户自定义 API Key 的完整安全交互；
- 根据脸型、当前长度、发质、发旋、发际线和理发师能力计算的现实可剪性引擎；
- “理想造型图 vs 日常不打理状态”的真实比较；
- 自动把“下次微调”和避雷经验写入新计划并进行冲突提示；
- 真正离线 PWA；
- 统一生成剪前/剪后对比图、复盘图和外部分享模板；
- 邮箱验证码登录和跨设备同步；
- 基于真实目标用户的 P80 完成时间、理发师 10 秒理解率和长期留存验证。

## 6. 参考借鉴与高价值部分

### Apple / iOS 交互原则

借鉴的不是“所有地方做玻璃”，而是：

- 用户触摸时立即反馈；
- 手指拖出目标时取消，松开时回弹；
- 一个屏幕只突出一个关键决定；
- 空间位置和对象保持稳定；
- 动效服务于因果关系，不做无意义装饰；
- 尊重减少动态、减少透明度、字体放大和触控面积；
- 照片和内容优先，材料层只用于导航与操作。

### Linear 式克制

- 主任务优先，次要设置渐进展开；
- 用排版、留白和分隔建立层级，避免“卡片套卡片”；
- 状态和动作使用短而明确的语言；
- 减少首页同时出现的竞争入口。

### iOS Photos 的个人记忆感

- 让照片成为个人档案和历史的第一视觉锚点；
- 用剪前/剪后对比建立“这是我的数据”；
- 历史记录不是流水账，而是下一次复刻或避雷的证据。

### Product-Manager-Skills

- 从用户问题、使用场景、解决方案、验收和优先级推进；
- 用真实核心闭环替代功能堆砌；
- 把社区、支付、商家端等高成本非核心能力明确排除；
- 当前阶段采用价值/工作量排序，而不是用缺乏真实数据的 RICE 制造精确假象。

### OpenAI Product Design / Audit

- 先审计现有页面和真实流程，再定义视觉目标，再实现；
- 区分“代码能运行”和“用户能理解”；
- 检查空状态、加载、失败、权限、设备和无障碍，而不只看理想页面；
- 每次视觉重构后重新进行 Design QA。

### Playwright Interactive / 自动化验收

- 在真实浏览器中完成点击、上传、刷新、拖动和删除；
- 覆盖移动端和桌面；
- 验证无横向溢出、触控尺寸、键盘焦点和减弱动画；
- 检查网络请求，证明本地隐私链路没有把原图或私密字节发送出去。

## 8. 当前主要问题与风险

### P0：记忆还没有真正影响下一次

历史已经能保存，但用户“下次微调”的文字、避雷规则和成功经验没有完整自动带入下一次计划。当前产品更像一个高完成度档案工具，还没有完全成为“越用越懂我”的决策助手。

### P0：理发现场离线保证不足

现场页和导出图可用，但浏览器在断网、系统回收页面或微信内置浏览器重新打开时，不保证原页面仍可用。理发现场属于关键时刻，必须提供更确定的离线兜底。

### P1：分享产物不完整

目前有沟通卡和隐私遮罩导出，但用户还不能一键生成统一的剪前/剪后对比图、复盘图和适合微信/小红书的本地分享图片。

### P1：现实可剪性仍偏静态

当前能表达要求和风险，但不能自动判断“现在的长度能否剪到目标”“发旋/发际线会不会冲突”“是否依赖烫发或高强度打理”。

### P2：真实 AI 尚未进入产品

现有 AI 页面必须继续标注示例体验。没有真实质量样本、失败拦截、供应商删除边界和成本控制之前，不应把它宣传为真实本人试剪。

### 发布风险

- 当前是本地优先 H5，不代表已完成正式云端生产发布；
- 私有 GitHub 仓库是源代码归档，不等于公开用户访问地址；
- Vercel、真实域名、国内网络稳定性、云端数据库和生产环境变量不在本汇报的“已完成”范围；
- 邮箱登录、真实 AI、跨设备同步和正式商业运营均不能宣称已经上线。

## 9. 建议的下一步

按“用户价值 / 工作量”排序，建议不要先扩充发型库，也不要先接真实 AI。

### 第一优先：让历史真正自动影响下一次

目标：用户新建计划时，系统主动带入上次的成功点、微调点和避雷点，并明确告诉用户“这次已经替你记住了什么”。

建议包括：

- 把“下次微调”自动带入新计划和沟通卡；
- 把有效避雷规则与候选要求做冲突提示；
- 首页显示本次已继承的个人经验；
- 用户可一键删除或修改自动带入项；
- 自动继承必须有来源说明，不黑箱修改用户计划。

### 第二优先：理发现场离线保证

目标：即使现场网络差，用户仍能打开最后一张沟通卡。

建议包括：

- 最后一张沟通卡本地缓存；
- PWA/service worker 或等价离线打开能力；
- 显式“已准备离线使用”状态；
- 微信内置浏览器无法可靠离线时，强提示用户提前保存图片；
- Android Chrome、iOS Safari 和微信内置浏览器做真实断网复验。

### 第三优先：本地分享文件工作室

目标：不做社区，也能让用户把成果发到微信、小红书或保存相册。

建议包括：

- 剪前/剪后对比图；
- 本次复盘图；
- 沟通卡分享图；
- 隐私遮罩图；
- 系统分享或下载兜底；
- 全部在本地 Canvas 生成，不上传原图，不带追踪参数。

### 第四优先：再决定是否接真实 AI

只有在核心闭环经过真实用户验证后再做：

- 默认模型或用户自定义 API Key；
- 单视角真实试剪；
- 输入质量检查和失败拦截；
- 明确的 AI 标识；
- 服务商数据留存与删除说明；
- 至少 30 张授权成年样本的发布前质量门槛。

## 10. 建议外部 AI 重点评审的问题

1. 当前“档案 → 计划 → 沟通卡 → 剪后复盘”的信息模型，是否足以支持自动记忆继承？
2. 如何在不增加认知负担的前提下展示“系统替你带入了什么”？
3. 避雷规则与新候选冲突时，怎样提示最可信、最不打扰？
4. H5 在 iOS Safari、Android Chrome 和微信内置浏览器中，离线沟通卡的最低可靠方案是什么？
5. 本地 Canvas 分享图如何同时保证清晰度、隐私、中文排版和低端手机性能？
