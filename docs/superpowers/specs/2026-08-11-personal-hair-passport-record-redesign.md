# “咋剪发”个人发型护照与真实理发记录重构规格

> 日期：2026-08-11
> 状态：基于已批准的全页面 UX 审计进入实施
> 适用规则：根目录 `AGENTS.md`
> 来源：`docs/product-reviews/2026-08-11-adversarial-product-ux-audit.md`

## 1. 执行摘要

第一批优化把“通用文字档案 + 六阶段研究式记录”改造成一个完整、可见的个人闭环：用户用一张当前头发照片和最少条件建立个人发型护照，立即得到本地、可解释的精选排序；理发后只需保存剪前或剪后照片即可留下记录，补齐两张后形成直观对比；再次打开应用时首先看到自己的照片、最近结果和唯一下一步。

本批保留现有 IndexedDB、本地图片处理、私人参考、计划、沟通卡、标准发型和避雷数据，不推倒已有技术底座。旧六阶段照片继续读取和展示，但不再出现在新记录主流程，也不再触发首页补录。

## 2. 问题与目标用户

### 2.1 主要问题

- 用户填写的档案没有照片，无法产生“这是我的头发”的身份感。
- 性别资料与发型呈现偏好缺失，且现有头发条件没有参与发型解释。
- 新记录默认满分和复刻，造成未经用户确认的错误历史。
- 六个照片阶段、双列输入和原生文件控件违背理发后的真实手机场景。
- 档案总览以数据库分区为中心，没有剪前/剪后照片墙和最近结果。
- 现有记录结果存在低对比度，部分按钮与卡片缺少明确可操作性。

### 2.2 主要用户

18 岁以上、没有发型专业知识、担心理发翻车的短发用户。用户可能是女性、男性、非二元或不愿披露性别；推荐不能用性别身份限制可查看内容。

### 2.3 核心 Job

> 当我不知道什么适合自己、又不想维护复杂资料时，我希望用自己的照片和少量真实条件得到可信方向；剪完后快速保存前后差异，让下次更容易复刻或调整。

## 3. 方案选择

### 方案 A：一次性重写全部 P0 页面

优点是最终形态统一；缺点是同时改档案、记录、计划、沟通卡、理发师模式和导出恢复，风险与回归面过大，难以判断哪一部分真正改善体验。本批不采用。

### 方案 B：只修 CSS、字号和按钮

优点是见效快；缺点是用户仍只得到通用文字档案和六阶段记录，无法解决个性化与业务逻辑错误。本批不采用。

### 方案 C：纵向闭环分批重构（采用）

先交付“当前头发 → 个性化解释 → 剪前/剪后记录 → 回访照片墙”的完整价值，再扩展沟通卡和理发师现场工具。每一批均可由用户独立完成真实任务，并能在手机上验收。

## 4. 优先级与阶段边界

本项目处于公开体验前、数据有限、资源有限阶段，采用“用户价值 × 上线风险 × 工作量”的 Value/Effort 判断，并以 Must/Should 控制范围。

### 本批 Must

1. 修复记录结果低对比度。
2. 档案增加本机照片、性别资料、发型呈现偏好和当前困扰。
3. 所有未知资料默认“暂不确定”或未选择。
4. 发型库根据已确认档案条件做本地可解释排序。
5. 新记录仅显示剪前、剪后两个照片槽，旧阶段只兼容读取。
6. 满意度与下次意愿不设默认答案。
7. 增加纯文本店铺位置。
8. 档案首页展示当前照片、最近剪前/剪后和最近三次剪后照片。
9. 移除首页洗后、第 7 天补录任务。
10. 重构受影响页面的移动端单列布局、固定层、按钮与交互卡片状态。

### 下一批 Must

- 候选主方案收敛与现实风险对比。
- 精选指南、档案偏好和启用中的避雷规则自动生成沟通卡草稿。
- 理发师一屏模式、图片放大和屏幕常亮。
- 本机数据导出/导入。

### 暂不进入

- 社区、帖子、评论、点赞或公开投稿；
- 账号、云同步、微信或手机号登录；
- 地图服务、定位权限或店铺数据库；
- 真实 AI 推荐、试剪或远程人脸分析；
- 支付、会员、积分、兑换码和理发师端。

## 5. 用户流程

### 5.1 第一次建立个人发型护照

1. 首页只给一个主操作：“先让应用认识我的头发”。
2. 第一步上传当前正面照片；侧面和后脑可选。图片使用现有本地纠正、压缩、重绘和去 EXIF 管线，只保存处理后 Blob。
3. 第二步选择称呼、性别资料和发型呈现偏好。
4. 第三步填写发质、粗细、发量、可接受打理时间与当前困扰；未知项保持未确定。
5. 保存后进入个人发型护照，首屏显示用户照片、简短条件摘要和“看看更适合我的方向”。
6. 发型库至少将三款内容放入“更符合你当前条件”，逐款说明匹配依据和现实取舍；条件不足时明确说“按精选顺序展示”，不冒充个性化。

### 5.2 理发后快速记录

1. 用户进入“记录这次理发”。
2. 首屏只展示剪前、剪后两个中文照片槽；至少保存其中一张，补齐两张后形成对比。
3. 日期默认今天，这属于可靠上下文默认值；发型名、满意度和下次意愿均允许暂不填写。
4. 用户主动选择满意度；主动回答“下次还想这样剪吗？”时，可选“想复刻”或“有些地方要调整”。
5. 店铺、店铺位置、理发师、服务、价格、耗时和备注放入“补充本次信息”。
6. 保存后直接进入记录详情，先看到同尺寸剪前/剪后，再看到结论和补充信息。

### 5.3 第二次打开

1. 档案首页优先显示当前照片或最近剪后照片。
2. 有完整前后照时显示最近一次对比；只有一张时如实显示已保存阶段和待补照片，不阻止继续使用。
3. 展示最近三次剪后缩略图；点击进入对应记录。
4. 只给一个基于当前状态的主操作，不再追着用户补洗后或第 7 天照片。

## 6. 数据契约

### 6.1 HairProfile

新增：

```ts
type GenderIdentity =
  | 'woman'
  | 'man'
  | 'non_binary'
  | 'self_described'
  | 'prefer_not_to_say'
  | 'unsure'

type PresentationPreference =
  | 'feminine'
  | 'masculine'
  | 'androgynous'
  | 'open'
  | 'unsure'

type HairConcern =
  | 'flat'
  | 'frizz'
  | 'cowlick'
  | 'hairline'
  | 'growing_out'
  | 'hard_to_style'

interface HairProfile {
  genderIdentity: GenderIdentity
  genderSelfDescription?: string
  presentationPreference: PresentationPreference
  concerns: readonly HairConcern[]
}
```

旧档案读取时使用 `unsure` 与空数组补齐，不覆盖用户已有字段。新档案的发质、粗细、发量、洗发频率也默认 `unsure`；打理时间默认 `null`。

### 6.2 HairProfilePhoto

新增独立表，避免把多个 Blob 塞进 profile 行：

```ts
interface HairProfilePhoto {
  id: string
  profileId: string
  angle: 'front' | 'side' | 'back'
  image: Blob
  width: number
  height: number
  bytes: number
  processedAt: string
  updatedAt: string
}
```

同一档案、同一角度最多一张当前照片。替换图片必须是原子操作；失败时保留旧图及其全部元数据。

### 6.3 HaircutRecord

- `styleName` 改为可选；为空时界面显示“这次理发”，不向存储写伪造发型名。
- `satisfaction` 改为 `1 | 2 | 3 | 4 | 5 | null`。
- `outcome` 增加 `undecided`；`repeat` 与既有 `avoid` 继续兼容。界面将 `avoid` 表达为“有些地方要调整”。
- 增加可选 `salonLocation` 纯文本字段。
- 新记录允许 `before` 与 `after` 阶段；至少需要其中一张。
- `during`、`unstyled`、`styled`、`after_wash`、`day_7` 只在旧记录读取、编辑兼容区和详情“历史其他照片”中出现。

### 6.4 IndexedDB 迁移

- 新增版本仅声明需要的新表或索引，不重写旧图片 Blob。
- 所有旧档案和旧记录通过 read hook 或纯归一化函数补齐默认值。
- 迁移前后的旧六阶段图片字节、ID、顺序和关联关系必须保持不变。
- 更新 profile、profile photo 或 record 时使用单一 Dexie 事务，失败不得留下半份新数据。

## 7. 个性化排序规则

个性化只使用用户已确认的数据：

- 发质命中：正向依据；
- 发丝粗细命中：正向依据；
- 发型呈现偏好命中：正向依据；`open` 不加分也不扣分；
- 日常打理时间与内容维护等级：转为现实取舍；
- `unsure`、未填写和性别身份不参与排序。

输出规则：

- 不展示匹配百分比或“AI 推荐”；
- 每款最多显示两条“为什么更适合你”和一条“需要考虑”；
- 不符合某项不等于禁止查看，只改变排序并诚实解释；
- 有效条件不足两个时保持原精选顺序，并显示“补充头发条件后可为你排序”。

## 8. 页面与交互设计

### 8.1 视觉论点

简约白色 iPhone 工具感：照片是最强视觉锚点；彩色小图标帮助扫描；普通内容保持平静；只有可点击卡片和浮动控制层拥有体积。界面应让用户感觉“这是我的私人发型相册和决策工具”，而不是后台表单。

### 8.2 三层表面

1. 内容层：照片、正文和时间轴直接落在白色或极浅灰背景，不套无意义卡片。
2. 交互卡片层：1px 受光边缘、克制阴影、明确方向提示；按下时缩放约 0.97、阴影收紧。
3. 浮动控制层：仅底部导航、页面唯一操作坞或 sheet 使用浅色半透明材质；每页最多一个固定层。

### 8.3 按钮与触摸

- 主按钮使用稳定实色、图标与动作动词；次按钮使用浅色实体或清晰描边；主要提交不得伪装成文字链接。
- `pointerdown` 后下一帧反馈；手指停留不提交；拖出约 10px 取消，拖回恢复，松手才提交。
- 回弹从当前显示状态开始并可被新触摸中断。
- 减少动态时取消缩放弹簧和大位移，保留颜色、轮廓和短淡变。
- 所有新触控目标至少 44 × 44px，正文至少 15px。

### 8.4 受影响页面

- `/`：有档案时展示用户照片或最近剪后；唯一主动作来自真实状态。
- `/archive/profile`：照片先行的三段渐进表单；删除进入独立危险区域；沉浸表单隐藏全局底栏。
- `/archive`：改为个人护照、最近前后对比、最近三次照片和唯一下一步；不再一次堆六个空分区。
- `/styles`：增加“为我排序”状态、个性化原因和条件不足提示。
- `/archive/records/new`、`/edit`：单列、两个照片槽、附加信息折叠、无默认答案；沉浸表单隐藏全局底栏。
- `/archive/records/:id`：前后对比优先；修复结果对比度；历史其他照片折叠展示。

## 9. 用户故事与验收

### Story 1：一分钟建立属于我的档案

- **作为**第一次使用、没有发型知识的用户
- **我想要**用照片和最少的真实条件建立档案
- **以便**立即确认应用认识的是我的头发，而不是一份通用资料。

**场景：首次建档**

- **Given** 我没有档案且没有账号；
- **When** 我上传当前照片、选择已知条件并保存；
- **Then** 我在个人发型护照首屏看到处理后的本人照片、已确认条件和唯一下一步。

### Story 2：知道哪些精选更值得先看

- **作为**不知道剪什么的用户
- **我想要**看到基于自己已确认条件的排序和解释
- **以便**减少浏览和猜测，而不被虚假的 AI 分数误导。

**场景：有足够档案条件**

- **Given** 我的发质、粗细和呈现偏好已经保存；
- **When** 我打开精选发型库；
- **Then** 至少三款内容按本地规则排序，并显示匹配依据与现实取舍。

**场景：条件不足**

- **Given** 我只保存了一张照片或大量条件仍不确定；
- **When** 我打开精选发型库；
- **Then** 页面保持精选原顺序，并明确说明没有冒充个性化。

### Story 3：一分钟留下这次理发

- **作为**刚理完发、只想快速记住结果的用户
- **我想要**只处理剪前和剪后照片
- **以便**不在理发现场或回家后填写一套研究记录。

**场景：新建记录**

- **Given** 我已有档案；
- **When** 我添加至少一张剪前或剪后照片并保存；
- **Then** 记录成功保存，满意度和下次意愿不会被自动填写。

### Story 4：下次回来直观看懂上次结果

- **作为**准备再次理发的回访用户
- **我想要**首先看到自己的剪前/剪后对比、店铺位置和结论
- **以便**快速决定复刻还是调整。

**场景：查看历史**

- **Given** 我已有包含前后照片的记录；
- **When** 我打开档案或该记录；
- **Then** 页面优先显示同尺寸对比、最近照片和已确认结论，且不要求补洗后或第 7 天照片。

## 10. 错误、隐私与兼容

- 图片处理失败时不写入原图或半成品，并允许重新选择。
- 存储空间不足时保留当前表单输入和旧数据，明确说明未保存。
- Object URL 在替换、离开和卸载时回收；迟到的图片处理结果不能覆盖用户后选图片。
- 所有照片仅保存在当前浏览器；本批不上传，不增加网络请求。
- 性别资料允许不愿透露；自定义文本仅按纯文本显示，不用于硬限制推荐。
- 旧档案、旧记录、旧标准发型、旧避雷规则和旧六阶段照片必须继续可读、可编辑、可删除。

## 11. 验证门禁

### 自动化

- Repository：迁移、Blob 保留、profile photo 原子替换、record 新旧模型兼容。
- Store：无默认答案、至少一张前/后照片、保存失败保持旧状态、个性化排序输入。
- Unit/UI：渐进表单、个性化/非个性化文案、历史阶段折叠、低对比回归。
- E2E：首次建档 → 个性化精选 → 保存前/后记录 → 刷新 → 档案照片墙 → 记录详情。
- 网络：上述完整流程不得产生图片上传、外域请求或原始字节请求体。

### 真实视觉

- 360 × 800、390 × 844、430 × 932；
- 200% 字体、减少动态、减少透明度；
- 空数据、处理中、成功、失败、旧数据兼容和最密集真实状态；
- 检查照片不被错误裁切、固定层不叠加、单列不折叠、按钮与信息区可仅凭外观区分；
- 检查按下、拖出、拖回、松手和保存反馈，而不是只拍静态截图。

### 任务成功标准

- 无教程的首次用户可在 60 秒内完成最小档案并看到本人照片；
- 用户可在 60 秒内保存一次新模型理发记录；
- 第二次打开后，首屏能识别本人照片、最近结果和一个明确下一步；
- 功能、布局、视觉和真实任务四项分别通过，不能互相替代。

## 12. 风险与缓解

- **范围过大**：按垂直用户故事依次交付，不拆成只有数据库或只有 CSS 的横向任务。
- **旧数据回归**：迁移不重写 Blob，历史阶段使用只读兼容路径并有字节级测试。
- **个性化过度承诺**：只解释显式规则，不展示百分比，不使用性别身份作为过滤门槛。
- **CSS 再次覆盖冲突**：受影响页面逐页删除旧 selector，使用语义 token；禁止新增 `!important` 修补。
- **动效影响效率**：反馈必须即时、可中断；减少动态提供等价状态；不得为动效增加等待。

## 13. 后续里程碑

2. 沟通卡自动继承与理发师一屏模式；
3. 本机数据导出/导入；
4. 计划、沟通卡、遮罩和“我的”逐页视觉重构；
5. 发型库内容覆盖矩阵与真实理发师/用户任务测试。
